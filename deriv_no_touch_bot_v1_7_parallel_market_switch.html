V1 logic: estimate the probability that each candidate barrier will be hit within the configured tick duration using historical tick paths normalized by local volatility. Score both barrier sides locally, select the barrier with the lower estimated touch probability, derive No Touch probability as its complement, request live proposals only for No Touch candidates, then rank them by expected value using the quoted payout. A trade is only entered when probability, payout band, and EV thresholds pass. Real mode is disabled unless explicitly armed.
Proposal-rate protection: all proposal requests now share one paced queue. Active execution requests have priority; parallel-monitor requests are limited to one candidate per scan and cached briefly. The queue targets no more than 4 proposal requests/second and pauses for 15 seconds after a rate-limit response. This keeps the bot below Deriv's documented 360 proposal/proposal_open_contract/buy/sell requests-per-minute budget while still allowing continuous market monitoring. Deriv documents these calls as a shared 360/min and 14,400/hour WebSocket budget.
Money-management scope: martingale applies only to the active market execution. Parallel monitoring remains at the base stake so market WR15 measures the underlying No Touch strategy rather than being distorted by recovery sizing.
Parallel monitoring: while one market is traded, the other configured markets continue receiving live ticks through a separate public WebSocket. They run the same No Touch barrier model in paper mode and contribute completed results to their rolling 15-trade market performance. Only the active market can place a real trade.
Auto-switch: after 2 consecutive losses, the bot pauses. If enabled, it selects a different eligible market only when that market has at least 15 completed strategy observations and a higher rolling win rate. The switch uses the already-running parallel model state; it does not reconnect or request new history.
Money management: Fixed-factor martingale uses Base × Factorstep, capped by Max stake. Payout-aware martingale uses the live quoted return to target accumulated losses + the configured recovery target profit. A win resets the recovery step and pool. The recovery target is separate from the session profit target.
Current ladder: Payout-aware — calculated from live payout
Recovery: payout-aware recovery uses the actual quoted return, so the next stake is based on the accumulated loss pool plus the configured recovery target. A win resets recovery. Session target/loss stop operate independently.
